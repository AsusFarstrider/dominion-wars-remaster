# Launch-selected dimensions: earliest binding and HD fitting

2026-10-30. Bounded source/lifecycle assessment for Rendering's authorized adaptive-resolution prototype. **A detour of the existing EXE CRT entry is the smallest plausible early binding point. A new .dwui startup stub is unnecessary for this purpose.** This is design support, not approval of an unseen bridge implementation or proof of arbitrary-mode operation. Engine modified no executable/runtime and ran no build, fixture or game.

## Confirmed ordering

Both the original and existing input-control800×600 EXE statically import DDRAW.dll, have image base400000, entry4B085A, initial bytes `55 8B EC 6A FF`, and no PE TLS directory. The stable input-control EXE SHA256 is `e81aacb185e755c6478c06516bf0d442b7b95edc1f3a3603bfc7ecda1c777023`. All15 dimension/projection instructions still equal the original in that file.

1. Static wrapper process attach occurs before the EXE entry. Current DllMain loads managed configuration and installs the Bink safety imports here. This gives time to install a future-entry detour, without selecting display dimensions under loader lock.
2. Original entry4B085A calls CRT initialization4B0CE4 at4B08FF, before calling WinMain433B40 at4B0935. CRT initialization iterates4C1000..4C11FC; pointer4C11EC names4A63F0, which calls4A6460. Consequently default writes4A6480/87 execute before WinMain.
3. WinMain first calls429940, whose configuration helper4294E0 reads GetSystemMetrics(0/1) through IAT4BD214, stores the original mouse-recenter cache AB9EE4/6, and initializes input rectangle A38620 with fixed800×600 operands429883/88. These metrics are not the engine's display request. The stable input-control EXE separately refreshes the recenter cache from GetClientRect at use; retain that behavior.
4. WinMain constructs the application, then virtual+18 runs before+24 and+28. Table4BDA10 maps+24 to433490 (screen initialization) and+28 to434230 (application initialization).433490 supplies fixed W/H to4A6510;4A6510 stores them before entering DirectDraw enumeration. Its first public DirectDraw call therefore observes an already-written request.
5. Later application initialization4285C0 consumes initial layout operands428C84/89, builds layout from the screen object, and calls mission-default writer42B5B0 at428E16. Reset requests4292D9/DE and4AD865/6A plus mission projection40117A remain independent future consumers.

The existing first-export `Remaster::initialize()` is too late for the CRT defaults, input initialization and the initial screen-request arguments. It is not a replacement for early binding, even though some later layout/mission writers have not yet run.

## Entry-detour assessment and concrete hazards

Installing the detour during validated **static** process attach, then selecting and binding dimensions when the loader transfers to the EXE entry, places setup before all those consumers and outside DllMain. The exact first three instructions occupy five bytes and contain no relative addressing, so the current trampoline copier can relocate that specific prologue. A preserved-state naked bridge must call a noexcept DLL-side binder once, restore its saved stack/registers/flags and any FP state it changes, then jump to the trampoline. No guessed QUANTUM function signature is needed. The DLL's CRT has initialized; the EXE's CRT has not. Do not depend on EXE heap, globals with constructors, diagnostics readiness or engine subsystems in the binder.

`Compat::hookFunction` is not a checked installation transaction: it has a void return, unchecked VirtualAlloc/VirtualProtect results and only limited instruction relocation. Exact prologue validation makes relocation tractable here, but does not repair allocation/protection failures. Installation needs checked storage/protection, an unambiguous failure result and verified destination/trampoline bytes before readiness is claimed; ordinary exceptions must not escape DllMain. Existing Bink safety uses **IAT replacement**, not this prologue detour. Its success is not evidence of a working EXE-entry hook. Reject dynamic late loading or an already-replaced entry rather than following an unknown hook chain.

Bind one canonical launch W/H pair (the proposed DW_REMASTER_OUTPUT_WIDTH/HEIGHT pair) after validation against the primary-origin0 physical mode contract. Keep dimensions fixed for this process. Validate all15 complete original instructions before changing any operand, check memory protection and readback, restore original page protections and flush instructions; failure must stop before original CRT proceeds with partial state. A shared binding record should drive mode policy and diagnostics. No dimension-dependent on-disk EXE or new export/import is required.

The15 existing sites cover seven W/H pairs: initial layout, mission defaults, screen-object defaults, initial screen request, generic reset request, initial input rectangle and application-transition request; plus m11 at40117A. They are a bounded existing policy map, not proof that every subsystem accepts every size. Keep the calibrated base m11 relationship `2*(800/W)*((H-154)/446)` with m22=3.5; HudAssembly already multiplies by `sceneHeight/(H-154)` when it reserves scaled HUD space. Pre-applying that correction would apply it twice. Rendering and picking must still share the resulting scene rectangle/projection.

**Existing guards need deliberate rebinding.** NativeProbe currently maps disk SHA to fixed W/H and aborts before mode application if the selected mode differs. Retain exact disk identity, but obtain its expected launch dimensions from the validated binding; do not disable selected-mode validation. Runtime::initialize's2560×1440 check and OpeningFlow's explicit DE3 executable hash also need consistent new-profile identities. Original4A6880 can overwrite requested W/H from the selected mode record, so an unavailable legacy16-bit mode must fail explicitly rather than silently produce mixed dimensions.

Do not use global GetSystemMetrics spoofing as the binder: original metrics serve mouse setup, and DDrawCompat later virtualizes screen/fullscreen metrics using emulated monitor dimensions. Query the intended physical mode outside loader lock, with wrapper bypass/original API semantics if those hooks are already present. Microsoft recommends minimal loader-lock work and cautions against User32/GDI calls there ([DLL best practices](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices)). Current attach-time complexity is not a reason to add display selection there.

## Reuse for HD movies

The frozen HD provider is **identity-output only**, not an existing general HD-to-target fitter. HdHistory owns source W/H/pitch and full conversion history correctly. copyHd requires target==history W/H, then calls history.identity; Unlock repeats that equality, and the HD input predicate requires2560×1440. Changing only the row copy will leave publication/input refusing other targets.

Reuse `MenuCanvas::Plan::fit(sourceW,sourceH,targetW,targetH)` and its checked compose path. CardImage already demonstrates a direct identity fast path plus cached target-specific Plan, without traversing800×600. This is a nearest-cell RGB565 fit with uniform aspect and cleared margins; higher-quality resampling would be separate work. Keep HD asset identification/source2560×1440 independent of target size. Decode exactly once into the same source-resolution history with source pitch and XY0,0; retain full-copy flags until an actual conversion result0 initializes history, subsequent selective updates, seek invalidation, quarantine and Wait/DoFrame/NextFrame/Close ordering. Fit only the completed history to the current valid lease, then publish after matching successful Unlock.

Bind fitted output publication to movie lifetime, source revision, target dimensions/surface and lease generation; update copy, Unlock and input guards together. Preserve the existing whole-output skip policy unless deliberately changed: letterbox margins need not become a new dead input area. Pixel receipts for nonidentity output must compare against the fitted reference, not assert raw source==target hashes. Source history must never become target-sized or be reseeded from scaled native storage.

Existing HUD Layout::fit supports bounded W>=800/H>=600 through16384, not unrestricted resolutions or live resizing; target byte/area limits and allocation failures still apply. Phase1 can stay launch-only, primary-origin0, with explicit supported-mode refusal and focused validation. Nothing in this assessment requires a new renderer or broad engine reconstruction.
