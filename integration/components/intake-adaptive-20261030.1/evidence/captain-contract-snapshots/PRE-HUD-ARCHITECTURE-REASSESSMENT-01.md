# QUANTUM before HUD work: concise architectural handoff

2026-10-25. For Rendering. Review of existing Rendering/Resolution results, original-engine exports and accepted submenu/loading receipts. **Recommendation: retain native engine scene rendering and extend the successful owner-scoped UI approach to one complete HUD group. Repair shared layout/coordinate boundaries where evidence permits; do not scale the complete mission frame or reconstruct the whole HUD first.** No executable/HUD changes, new exports or experiments were performed for this review.

## 1. What changed

**Confirmed:** QUANTUM is not fundamentally an800x600 renderer. The native1440 experiment joined accepted mode, actual draw/depth targets, scene2560x1286, projection/picker and1:1 final presentation; the user passed mission interaction. Subsequent opening tests passed both factions, and run04 passed Preferences, Load, Credits, Multiplayer20, transitions and loading. Native scene plus independently fitted original-density UI is now a demonstrated research architecture on this system, rather than merely the leading hypothesis. DDrawCompat still supplies compatibility; wrapper resolution enhancement was disabled, not the wrapper itself.

**Corrected assumptions:** original software image/font operations can draw directly into the native target; an800x600 asset does not imply an800x600 intermediate framebuffer. The flattened menu canvas is our layout mechanism, not a discovered universal QUANTUM compositor. Native dimensions alone do not enlarge assets or UI. Run04 supersedes earlier “loading/submenus unvalidated” status;27/21/22 remain unvalidated in that accepted run. High-density captain-frame replacement was demonstrated separately, but through a textured-quad provider; CPU menu fitting does not establish denser artwork support.

**Still unproved:** general responsive resizing, exhaustive device recreation, other hardware/display combinations, a universal HUD layer or a small engine-only patch that replaces every UI adapter. No new evidence resolves NPOT-constructor defects, aggregate resource budgets or model-pool limits. The recorder's64MiB queue saturation was instrumentation overhead, not a discovered QUANTUM64MiB resource ceiling.

## 3. Coordinates, input and unresolved coverage

**Confirmed:** HUD initialization copies absolute layout values into packed widget coordinates. Resolution already found double translation when shifting both globals and their child consumers; shared values also feed D3D viewports. Historical+80 and−80 fixes belong to the960-wide baseline, not the native1440 arm. Notification494FC0 has its own fixed rectangles, separate from native world-label positions. CPU glyph metrics/wrapping and hardware sprite paths coexist.

World picking4070C0 uses scene dimensions and projection; scene input widget4DC530/id63 is separate from HUD controls. Preserve native world coordinates. Apply an inverse only to the matched HUD owner. Late input can arrive from the window procedure after draw/present, so the transform must belong to the most recently committed frame, not only an active paint scope. Generic rectangle conversion did not cover submenu sliders/list rows; captured drags also need endpoint/release handling outside the content rectangle. Expect HUD-specific consumers until a tested cluster shows otherwise.

**Unknown, bounded to the next test:** complete live producer/child membership of the first chosen group, portrait/text/animation overlap and CPU/GPU alternatives; its fresh underlay/opacity and cursor-save coverage; custom command, scan/minimap and preview input consumers; resource changes and faction-dependent identities. The existing native1440 clicking result validates the displayed small UI, not transformed HUD input. No need to enumerate every HUD control before exercising one complete group.

## 4. Smallest promising implementation

Start with the captain-control group as a **candidate**, including its real portrait/state overlays and events, rather than only enlarging its frame texture. Give it one logical rectangle, physical anchor/scale and committed input transform. Reuse the existing primitives and original callbacks once. Prefer the passed completed-panel snapshot/fit when its rectangle is proven HUD-only, freshly defined and free of a native preview/world image. Otherwise mirror supported primitive operations into an owned layer with explicit coverage; do not capture the already-composited world as a transparent background. This is an implementation choice for the bounded group, not a prerequisite to build a general HUD renderer.

Keep main scene and existing preview/minimap rendering native. Initially avoid changing scene reserve/projection unless the enlarged group actually needs that space; then update the reserve, clear extent, viewport, projection and picking coherently through the existing layout paths. A panel is a separate rendering role, not simply an image to stretch. One mission check should cover click/drag/release, changing selection/occupied state, a moving background or overlapping preview, a notification/modal interruption and normal return. Include the opposite faction only to the extent its actual resources/controls are exercised; opening-video acceptance is not HUD-family acceptance.

## 5. Simplifications and hazards

- **Targeted repair opportunity, not yet a proven replacement:** make479C60's widget-local placement and401860/429030's absolute viewport geometry consume one explicit layout policy. This can replace repeated per-coordinate offsets. Keep those coordinate domains distinct; do not globally spoof W/H or scale every TL draw/font call. Original parent-relative text can follow its subtree; genuinely direct font/notification rectangles need owner-scoped adapters.
- **No menu-style full-target black clear in a live HUD.**4023A9's bottom-strip clear is an existing bounded repair point; adapt its extent only with the HUD reserve. Transparent content requires coverage/underlay, not RGB565 black-as-alpha. Retire the original footprint and restore exposed background; do not leave both sizes or resample fitted history.
- **Publication is transactional.** Fresh target/Lock/pitch/palette, storage epoch, matched completion/Unlock and input epoch are reusable guards. Same COM address does not establish the same backing pixels. Mark potentially transformed storage before a write; failures must not reclassify it as unscaled. Busy/reentrant input invalidates pending publication. Withdraw the layer/input when its owner is hidden or destroyed;42A7B0 can skip widget traversal entirely.
- **One common phase is not every route.** Run04 proved ten direct loading presents, eight after UI detachment while current11/pending1. State commits occur after constructors; topology/state-only guards can reject legitimate work. Conversely, do not broaden a detached-loading exception into general detached HUD admission. Preserve original event/present count and visual-only causal departures.
- **Keep diagnostics subordinate.** Compact run04 had no producer stalls; the earlier heavy recorder saturated its queue. Use bounded receipts for the first HUD trial, not another exhaustive capture. Maintain existing image/glyph/resource identity, palette, masks and lease checks; bigger allocations and point filtering do not by themselves imply better artwork.

The unexpected architectural result is that reusable engine mechanisms were present, but ownership and mixed coordinate policy were the missing contract. Existing root-local routines, separate viewports and source-density separation can support a cleaner HUD without replacing QUANTUM. Whether every group can share one layer remains a hypothesis; one bounded implementation/test should answer the next question.
